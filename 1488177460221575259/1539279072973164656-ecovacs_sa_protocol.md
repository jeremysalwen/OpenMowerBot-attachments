# SA Protocol - Ecovacs UART Communication Protocol

**Model:** Ecovacs GOAT G1-800
**Reverse-engineered from:** `liberos_node_hardware_platform.so` (ROS Melodic node),
`libeco_navi.so`, `mcu_gkr.bin` (Main MCU), `top_mcu.bin` (Top/Screen MCU)
**Target:** Ecovacs robot motor controller (MCU)
**Interface:** UART @ 115200 baud, 8N1

---

## MCU Port Reference

Both MCU ports use SA Protocol.

| Port         | MCU            | SA Protocol | Update Method        | Description                         |
|--------------|----------------|-------------|----------------------|-------------------------------------|
| `/dev/ttyS8` | Main MCU       | **Yes**     | VP message -> YMODEM | Drive wheels, sensors, power, IMU   |
| `/dev/ttyS3` | Top/Screen MCU | **Yes**     | VP message -> YMODEM | Display, buttons, top sensors, LEDs |

Both ports are initialized with `protocol::SaMsgHandler` in `HardwarePlatformNode::initialize` (0x1b2400).

### Version Information Storage

After VP message, MCU responds with VB message. Versions are stored in `/tmp/mcu_verson.txt`:
- Main MCU: `main_version: <version>`
- Top MCU: `top_version: <version>`

## Frame Structure

```
` + SA + TYPE + TIMESTAMP + MSGID + PAYLOAD + CRC8 + \n
|   |    |       |          |       |         |     +- 0x0A (Newline, Frame End)
|   |    |       |          |       |         +- CRC-8/SMBUS (polynomial 0x07)
|   |    |       |          |       +- Variable length payload
|   |    |       |          +- 2 ASCII chars (e.g. "WD", "WA", "MA")
|   |    |       +- 4 bytes Little-Endian (ms since boot)
|   |    +- 0x02 = Data, 0x01 = Heartbeat
|   +- Magic bytes "SA" (0x53 0x41)
+- 0x60 (Backtick, Frame Start)
```

### Field Details

| Field      | Size | Description                                                            |
|------------|------|------------------------------------------------------------------------|
| Start      | 1    | `0x60` (backtick character)                                            |
| Magic      | 2    | `SA` (0x53 0x41)                                                       |
| Type       | 1    | Message type: `0x02` = RX data, `0x01` = heartbeat, `0x00` = TX common |
| Timestamp  | 4    | Little-endian, milliseconds since MCU boot (TX often uses random)      |
| Message ID | 2    | ASCII identifier (e.g. "WD", "WA", "HA")                               |
| Payload    | N    | Variable length, message-specific                                      |
| CRC8       | 1    | CRC-8/SMBUS over bytes from `SA` to end of payload                     |
| End        | 1    | `0x0A` (newline character)                                             |

### Escape Sequences

Applied **after** the `SA` magic bytes:

| Sequence   | Decoded Value  | Description       |
|------------|----------------|-------------------|
| `\x5C\x01` | `\x5C` (0x5C)  | Literal backslash |
| `\x5C\x02` | `` ` `` (0x60) | Literal backtick  |
| `\x5C\x03` | `\n` (0x0A)    | Literal newline   |

### CRC-8 Calculation

- **Algorithm:** CRC-8/SMBUS
- **Polynomial:** 0x07
- **Init:** 0x00
- **Scope:** Bytes from `SA` magic through end of payload (excludes CRC itself)

## Drive Wheels vs Auxiliary Motors

The drive wheels (left/right) are controlled with the WA (Wheel Action) message, not with MA (Motor Action).

| Function         | Message | Description                        |
|------------------|---------|------------------------------------|
| **Drive Wheels** | **WA**  | Left & right wheel speed/direction |
| Auxiliary Motors | MA      | Brush, vacuum, lens, other motors  |

Motor IDs 10 and 11 in MA are for auxiliary motors (main brush, lens), not for the drive wheels!

## Critical: MCU Initialization Sequence

The MCU requires a specific startup sequence before wheel control works.
Without it the wheel motors do not arm, and the arming click stays absent.

### OEM Startup Sequence

Observed from ROS node captures and disassembly:

```
+-----------------------------------------------------------------+
|  1. RA (RTC Init)      - 8 bytes of zeros                       |
|  2. HA (Heartbeat)     - timeout=2 (~0.8 s, OEM default)        |  optional
|  3. GC (Gyro Calib)    - 00 00 payload (mode 0, no flash save)  |  optional
|  4. LA (Light Control) - 15 bytes (status LED init)             |
|  5. UC (Clock Sync)    - 5 bytes (timestamp sync)               |
|  6. WA (Wheel Arm)     - 19 bytes (STOP command arms the motors)|  arms motors
|  7. HA (Heartbeat)     - Confirm initialization                 |
+-----------------------------------------------------------------+
```

**Step 3 Note:** OEM sends GC with payload `00 00` (mode=0) which calibrates but doesn't
persist to flash. For permanent SENSOR_ERROR fix, use payload `00 02` (mode=2) instead!
See the GC message specification in the IMU Module section for details.

**Step 5 arms the motors.** Sending `WA` with speed=0 (stop) is what arms the wheel
motors, and the robot answers with a mechanical click. Without that click the wheels
ignore all following WA commands.

### Timing Requirements

| After Message | Delay | Notes                                |
|---------------|-------|--------------------------------------|
| RA            | 0ms   | No delay needed                      |
| HA            | 0ms   | No delay needed                      |
| GC            | 100ms | Allow calibration to start (if used) |
| LA            | 50ms  | Allow MCU to process LED init        |
| UC            | 0ms   | No delay needed                      |
| WA (arm)      | 50ms  | Allow motor controller to arm        |

### Python Implementation

```python
def initialize_mcu(conn, gyro_calibrate=False, gyro_save_flash=False):
    """Initialize MCU with OEM startup sequence.

    Args:
        conn: SAConnection instance
        gyro_calibrate: If True, send GC message during init (OEM behavior)
        gyro_save_flash: If False (default), use mode=0 (OEM default, non-persistent)
                         If True, use mode=2 (persists to flash)
    """

    # Step 1: RA (RTC Init) - 8 bytes zeros
    conn.send_message('RA', bytes(8))

    # Step 2: HA (Heartbeat) - timeout=2 (OEM default)
    conn.send_heartbeat(timeout=2)

    # Step 3: GC (Gyro Calibration) - OPTIONAL
    if gyro_calibrate:
        gc_mode = 0x02 if gyro_save_flash else 0x00
        conn.send_message('GC', bytes([0x00, gc_mode]))
        print(f"Gyro calibration triggered (mode={gc_mode}, save={gyro_save_flash})")
        time.sleep(0.1)  # Allow calibration to start

    # Step 4: LA (Light Control) - 15 bytes
    la_payload = bytes([
        0x00, 0x00, 0x01,  # Light 0
        0x01, 0x00, 0x00,  # Light 1
        0x02, 0x01, 0x0f,  # Light 2 (on, mode 0x0f)
        0x05, 0x00, 0x00,  # Light 5
        0x09, 0x00, 0x00   # Light 9
    ])
    conn.send_message('LA', la_payload)
    time.sleep(0.05)  # 50ms delay

    # Step 5: UC (Clock Sync) - 5 bytes
    timestamp = int(time.time() * 1000) & 0xFFFFFFFF
    uc_payload = bytes([0x00]) + struct.pack('<I', timestamp)
    conn.send_message('UC', uc_payload)

    # Step 6: WA (Wheel Arm/Stop) - this step arms the motors
    conn.stop_wheels()  # Sends WA with speed=0
    time.sleep(0.05)    # Allow motor controller to arm
    # You should hear a CLICK sound here!

    # Step 7: Final heartbeat
    conn.send_heartbeat(timeout=2)
```

## Critical: Heartbeat Requirement

The MCU requires regular heartbeat messages to enable motor control.

Without heartbeats, motors are disabled as a safety feature.

### HA - Heartbeat Alive (TX)

**Interval:** Every 300-400ms
**Timeout:** If no heartbeat received for `timeout_count * 400ms`, MCU disables motors

| Offset | Size | Type      | Description   |
|--------|------|-----------|---------------|
| 0      | 2    | uint16_le | Timeout count |

**Observed values:**
- timeout=2 (~0.8s timeout, observed in captures)
- timeout=50 (20 second timeout, default in some implementations)

**Example:**
```python
# Send heartbeat with short timeout (observed behavior)
payload = struct.pack('<H', 2)  # 0x02 0x00
conn.send_message('HA', payload)

# Or with longer timeout
payload = struct.pack('<H', 50)  # 0x32 0x00
conn.send_message('HA', payload)
```

## Firmware Update (OTA)

### Overview

Both MCUs use SA Protocol for firmware updates.

| Port         | MCU            | Update Method      |
|--------------|----------------|--------------------|
| `/dev/ttyS8` | Main MCU       | VP -> VB -> YMODEM |
| `/dev/ttyS3` | Top/Screen MCU | VP -> VB -> YMODEM |

The firmware update process:
1. Send VP message to trigger bootloader mode
2. MCU responds with VB message containing current version
3. MCU starts sending 'C' characters (YMODEM ready)
4. Transfer firmware via YMODEM-1K protocol
5. Wait for `AT+UPDATE: OK\r\n` confirmation

### VP - Version/Program (TX: 0 bytes) OTA TRIGGER

**Triggers the MCU to enter firmware update (bootloader) mode.**

| Field      | Value                  | Description                     |
|------------|------------------------|---------------------------------|
| Message ID | `VP` (0x56 0x50)       | Version/Program                 |
| Payload    | Empty (0 bytes)        | No payload required             |
| Response   | VB message + 'C' chars | Version info, then YMODEM ready |

**Frame Example:**
```
` + SA + 0x02 + [timestamp 4 bytes] + "VP" + [CRC8] + \n
```

**Disassembly references:**
- `OtaNode::Impl::sendStartOtaCmd` @ 0x10e7a4 (Main MCU VP)
- `OtaNode::Impl::sendStartScreenOtaCmd` @ 0x10ea34 (Screen MCU VP)

**Python Implementation:**
```python
def send_vp_message(ser):
    """Trigger firmware update mode on SA Protocol MCU"""
    frame = sa_build_frame(b'VP', payload=b"", msg_type=0x02)
    ser.write(frame)
    ser.flush()
    # MCU responds with VB, then sends 'C' characters for YMODEM
```

### VB - Version Board (RX: Variable) VERSION RESPONSE

MCU version response after VP message.

| Offset | Size | Type   | Description                      |
|--------|------|--------|----------------------------------|
| 0      | 1    | uint8  | Board ID                         |
| 1      | N    | string | Version string (null-terminated) |

**Board ID Mapping:**
| ID  | Name         | Port       |
|-----|--------------|------------|
| 0   | main_board   | /dev/ttyS8 |
| 1   | top_board    | /dev/ttyS3 |
| 2   | screen_board | /dev/ttyS3 |

**Disassembly references:**
- `OtaNode::Impl::onSaMsgReceved` @ 0x10e250 (VB handler, writes to `/tmp/mcu_verson.txt`)
- `ScreenInfo::Impl::onSaMsgReceved` @ 0x12e454 (Screen VB handler)

**Version Storage:**
- Main MCU: `/tmp/mcu_verson.txt` with prefix `main_version: `
- Top MCU: `/tmp/mcu_verson.txt` with prefix `top_version: `

**Python Implementation:**
```python
def decode_vb(payload):
    """Decode VB (Version Board) payload"""
    if len(payload) < 2:
        return None

    board_id = payload[0]
    version_bytes = payload[1:]
    null_idx = version_bytes.find(0)
    if null_idx >= 0:
        version_bytes = version_bytes[:null_idx]

    return {
        'board_id': board_id,
        'version': version_bytes.decode('ascii', errors='replace'),
    }
```

### Firmware Update Protocol Flow

Important (apply/switch flag):
- Send `VR` with payload `0x01` BEFORE `VP` when an OTA slot switch is required.
- If `VR` is not sent, the app writes `UpdateOTAStatusFlag = 0x44444444` (no switch).
  With `VR`, the flag becomes `0x33333333` (apply/switch).

```
Host                                      MCU (/dev/ttyS3 and /dev/ttyS8)
  |                                        |
  |---- VR Message ----------------------->|  Version Response (switch firmware image)
  |                                        |
  |---- VP Message ----------------------->|  Trigger bootloader
  |                                        |
  |<---- VB Message -----------------------|  Version info (board_id + version)
  |                                        |
  |<---- 'C' 'C' 'C' 'C' 'C' --------------|  YMODEM ready (5x 'C')
  |                                        |
  |---- YMODEM Header -------------------->|  Filename + size
  |<---- ACK + 'C' ------------------------|
  |                                        |
  |---- YMODEM Data Packets (1K) --------->|  Firmware data
  |<---- ACK ------------------------------|  (repeat for all packets)
  |                                        |
  |---- EOT ------------------------------>|  End of transmission
  |<---- ACK ------------------------------|
  |                                        |
  |---- Empty Header --------------------->|  Transfer complete
  |<---- ACK ------------------------------|
  |                                        |
  |<---- "AT+UPDATE: OK\r\n" --------------|  Update success
  |                                        |
```

| Parameter        | Value                            |
|------------------|----------------------------------|

## Additional TX Message Specifications

### UC - Clock Sync (TX: 5 bytes)

Timestamp synchronization between host and MCU.

| Offset | Size | Type      | Description                 |
|--------|------|-----------|-----------------------------|
| 0      | 1    | uint8     | Flags/status (usually 0x00) |
| 1      | 4    | uint32_le | Timestamp or sync value     |

**Examples:**
- `003aec0200` -> value = 0x0002ec3a = 191546
- `0022f00200` -> value = 0x0002f022 = 192546

---

### LA - Light Control (TX: 15 bytes)

Controls status LEDs (5 light control blocks of 3 bytes each).

| Offset | Size | Type  | Description                               |
|--------|------|-------|-------------------------------------------|
| 0-2    | 3    | bytes | Light block 0: [light_id, param1, param2] |
| 3-5    | 3    | bytes | Light block 1: [light_id, param1, param2] |
| 6-8    | 3    | bytes | Light block 2: [light_id, param1, param2] |
| 9-11   | 3    | bytes | Light block 3: [light_id, param1, param2] |
| 12-14  | 3    | bytes | Light block 4: [light_id, param1, param2] |

**Observed payloads:**
```
00 00 01  01 00 00  02 01 0f  05 00 00  09 00 00
00 00 01  01 00 00  02 00 01  05 00 00  09 00 00
```

**Note:** Handler is `common::Light::onSaMsgReceved`. Likely controls status LEDs, not line laser.

| 0-7    | 8    | bytes | All zeros observed |

### RB - RTC DateTime Set (TX: 7 bytes)

Sets the MCU real-time clock.

| Offset | Size | Type      | Description                  |
|--------|------|-----------|------------------------------|
| 0      | 2    | uint16_le | Year                         |
| 2      | 1    | uint8     | Month (0-based or reserved?) |
| 3      | 1    | uint8     | Day                          |
| 4      | 1    | uint8     | Hour                         |
| 5      | 1    | uint8     | Minute                       |
| 6      | 1    | uint8     | Second                       |

**Example:** `ea07000a0e3817`
```
Year: 0x07ea = 2026
Month: 0x00 (January or reserved)
Day: 0x0a = 10
Hour: 0x0e = 14
```

##### Cut Motor Variable Speed Control

**Confirmed from disassembly of `libeco_navi.so` (navigation binary, 0x294298 setCutMotorInfo,
0x295090 calCutMotorSlowRatio, 0x248800 cutControl) and `liberos_node_hardware_platform.so`
(0xFB290 cut_motor_ctrl logging, 0xFD370 onSaMsgReceved MB/MS handlers).**

The cut motor accepts a uint16 speed value via the MA command. The OEM uses speed=37 (0x25)
as the fixed ON value, but the protocol supports arbitrary speed values for variable blade RPM.

**Command format:** `[0x0A, 0x06, speed_lo, speed_hi]`

| Speed Value | Effect                                                |
|-------------|-------------------------------------------------------|
| 0           | Motor OFF                                             |
| 37 (0x25)   | OEM default ON speed                                  |
| 1-65535     | Variable speed (MCU drives motor at proportional RPM) |

**Prerequisite:** The GC message `[0x00, 0x00]` must be sent during initialization before
cut motor commands will be accepted by the MCU (part of the standard init sequence).
GC belongs in the boot sequence once. It is Gyro Calibration, not a
"grass cutting mode": re-sending it with every blade command triggers a fresh
gyro calibration each time.

**The blade only spins while the wheels turn.** The LL board drops an MA cut
motor command issued on a standing robot, and nothing re-triggers it once the
wheels start. Two consequences for a host:

- Re-send the last non-zero cut motor command periodically (the ESP32 hub uses
  500 ms), the same way WA is re-sent while driving.
- Gate that repeat on measured wheel motion (from WD tick differentiation).
  Without a gate, wheel dither flickers the board's own motion detection and the
  blade cycles on and off at roughly 1 Hz on a parked robot.
- A spin-up self-test before driving is not possible on this hardware. Blade
  feedback (MB current, MS speed) only appears once the robot is moving.

An MA with speed 0 is always accepted, standing still included.

**OEM Cut Motor Control Flow (from `libeco_navi.so` disassembly):**

The OEM navigation binary uses cut motor control through a callback-based architecture:

1. `NaviTaskAssign::cutControl(int childLock, int cutCommand)` at 0x248800
   - cutCommand=0: sends callback(motor_id, 5, 0) = STOP
   - cutCommand=1: sends callback(motor_id, 3, 0) or (motor_id, 4, 0) = START
   - cutCommand=2: same as 1 with different log prefix
   - The callback maps abstract commands (3=start, 4=start-variant, 5=stop) to SA MA messages

2. The OEM does not send variable speed; it uses ON (speed=37) and OFF (speed=0).

**OEM Blade Load Feedback (from `libeco_navi.so` disassembly):**

The navigation binary reads blade motor telemetry (from MB/MS messages via SensorData) and
uses it to reduce DRIVE speed (not blade speed) when the blade encounters heavy load:

- `setCutMotorInfo(CutMotorSignal)` at 0x294298: Stores motor feedback from SensorData
  - SensorData offset 0xD0: signal type (int64)
  - SensorData offset 0xD8: two floats -- blade RPM and blade current

- `calCutMotorSlowRatio()` at 0x295090: Computes drive speed reduction ratio
  - Compares blade RPM against thresholds 5500 / 8000
  - Compares blade current against thresholds 1800 / 2000
  - Maintains 4 accumulation counters (capped at 10000 each)
  - Returns: 1.0 (full drive speed), 0.5, 0.3, or 0.0 (stop + move to another area)

- Configurable thresholds from `readCuttingNode` (OpenCV FileStorage config):
  - `cut_highcur_threshold_1`: default 40 (counter cycles for 0.5 ratio)
  - `cut_highcur_threshold_2`: default 60 (counter cycles for 0.3 ratio)
  - `cut_highcur_threshold_3`: default 100 (counter cycles for recovery to 1.0)
  - `cut_lowspeed_threshold_1`: default 50
  - `cut_lowspeed_threshold_2`: default 75

**Motor Type Configuration (from `liberos_node_hardware_platform.so` disassembly):**

The `cmotor` field in the robot config JSON determines MS speed reporting scaling:
- `"cmotor":"dechang"` -- MS speed values divided by 2
- `"cmotor":"lianyi"` -- MS speed values divided by 4
- `"cmotor":"kaihang"` -- MS speed values used as-is (1:1, no division)

Example config: `{"cmotor":"kaihang",...}` means raw MS speed = actual RPM.

**Example - Cut Motor ON (OEM default):**
```
0a 06 25 00  Speed = 37 (0x0025)
```

**Example - Cut Motor OFF:**
```
0a 06 00 00  Speed = 0 = OFF
```

**Example - Cut Motor at half speed (variable):**
```
0a 06 12 00  Speed = 18 (~50% of OEM default 37)
```

**Note:** Drive wheels are controlled via WA, not MA!

Each 3-byte block:
| Offset | Size | Type      | Description                     |

**Type to Index Mapping (from the lookup table at dword_1C0DF8):**

The raw type byte (1-8) is mapped through a lookup table: `internal_id = table[type - 1]`.
When `internal_id == 0`, the handler logs `cut_motor_current` with the current value.
When `internal_id == 11`, it logs `lens_motor_current`.

| Raw Type Byte | Internal Motor ID | Description                                                    |
|---------------|-------------------|----------------------------------------------------------------|
| 1             | 0                 | **Cut motor (blade)** -- current logged as `cut_motor_current` |
| 2-7           | 1-6               | Various auxiliary motors                                       |
| 8             | 11                | Lens motor -- current logged as `lens_motor_current`           |

The current value (uint16, mA) is stored in the motor state array at the internal ID's
slot and published as part of `motor/MotorCurrent`.

**Use case for blade load monitoring:**
The MB cut motor current combined with MS blade RPM provides real-time blade load data.
The OEM navigation binary uses these values in `calCutMotorSlowRatio()` (0x295090) to
dynamically reduce drive speed when the blade encounters heavy grass (see MA section above).

Publishes to: `motor/MotorSpeedReport`

### IMU Module (common::IMU)

#### GD - Gyro Data (RX: 21 bytes)

Layout confirmed from the Main MCU sender `sub_800B952` in mcu_gkr.bin.
All values are int16 little-endian and pre-scaled by the MCU (x 100).

| Offset | Size | Type     | Description                                                  |
|--------|------|----------|--------------------------------------------------------------|
| 0      | 1    | uint8    | Sub-type (always 0x02)                                       |
| 1      | 2    | int16_le | Heading / yaw from the AHRS fusion (x 100, 0x7FFF = invalid) |
| 3      | 2    | int16_le | AHRS rotation X (x 100)                                      |
| 5      | 2    | int16_le | AHRS rotation Y (x 100)                                      |
| 7      | 2    | int16_le | AHRS rotation Z (x 100)                                      |
| 9      | 2    | int16_le | Accel X (m/s^2 x 100, bias-compensated)                      |
| 11     | 2    | int16_le | Accel Y (m/s^2 x 100, bias-compensated)                      |
| 13     | 2    | int16_le | Accel Z (m/s^2 x 100, bias-compensated)                      |
| 15     | 2    | int16_le | Gyro X (rad/s x 100, bias-compensated)                       |
| 17     | 2    | int16_le | Gyro Y (rad/s x 100, bias-compensated)                       |
| 19     | 2    | int16_le | Gyro Z (rad/s x 100, bias-compensated)                       |

**Conversion:** divide every field by 100. The accelerometer is already in
m/s^2 and the gyroscope already in rad/s; no further scaling is needed.

**Sensors:** IIM-42652 (gyro + accel), QMC5883P (magnetometer). The AHRS
block is the 9-DOF fusion output, not raw magnetometer data. GD carries no
raw magnetometer axes -- use GI for those.

**Superseded reading:** earlier revisions of this document described GD as
raw gyro/accel/mag triplets with `radians = raw * pi / 18000.0`. That layout
does not match the MCU sender and is no longer used by any host here.

#### GH - Geomagnetic Hardware Status (RX: 6 bytes)

| Offset | Size | Type      | Description            |
|--------|------|-----------|------------------------|
| 0      | 1    | uint8     | Status (0 = valid)     |
| 1      | 2    | uint16_le | Raw compass value      |
| 3      | 2    | uint16_le | Combined compass value |
| 5      | 1    | uint8     | Compass level          |

**Use as a heading source.** GH carries the board's own fused compass output and
is the only heading the LL board offers. Scale and zero direction are not
established: forward the two counts unmodified and let the host decide, rather
than baking in a guessed conversion. Status and level travel with the sample so
a consumer can reject a bad reading.

The value is usable for differential checks (compare two GH samples of the same
quantity, for example dock heading now against dock heading at teach-in) without
knowing the scale. Any absolute use needs a turntable check first.

- Key globals:
  - `byte_20003794` - Calibration needed flag (checked in IRQ_37)
  - `byte_20003795` - Save to flash flag
  - `byte_20003B3C` - Calibration active indicator

**Handler Decompilation (0x80143CC):**
```c
switch (payload[1]) {  // Mode byte
    case 0:  // Mode 0: Calibrate WITHOUT flash save
        byte_20003795 = 0;  // save_to_flash = NO
        gyro_calibration_start(0, &byte_20003794);  // a1=0!
        byte_20003B3C = 1;  // calibration_active = YES
        break;

    case 1:  // Mode 1: flag only, no calibration
        byte_20003794 = 0;  // Just clear the flag
        // Does not call gyro_calibration_start()
        byte_20003B3C = 0;  // calibration_active = NO
        break;

    case 2:  // Mode 2: Calibrate WITH flash save
        byte_20003794 = 0;
        byte_20003795 = 1;  // save_to_flash = YES
        gyro_calibration_start(1, 1);  // a1=1!
        byte_20003B3C = 1;  // calibration_active = YES
        break;
}
```

**Calibration Process (0x800C39E) - Key Logic:**
```c
// After collecting 300 gyro samples...
if (a1 == 1) {  // only when mode=2 was used
    // Calculate bias averages
    word_20000716 = average_x;
    word_20000718 = average_y;
    word_2000071A = average_z;

    gyro_calibration_save_to_flash();  // Persist to flash!
    byte_20003794 = 0;  // Clear SENSOR_ERROR flag!
}
```

**Mode summary:**
- Mode 0 does not clear SENSOR_ERROR. It runs the calibration with `a1=0`, so the
  flash save and the flag clear are both skipped.
- Mode 1 clears the flag without running a calibration. The gyro bias values stay
  as they were.
- Mode 2 is the only mode that calibrates, persists to flash, and clears the
  SENSOR_ERROR flag.

**OEM Behavior (mode=0):**
```
OEM sends: 60 53 41 00 XX XX XX XX 47 43 00 00 YY 0A
```
- Calibration runs (collects 300 samples, calculates bias)
- Bias values stored in RAM only
- SENSOR_ERROR stays set
- On reboot, error returns because nothing was saved

**Mode 1 Behavior (flag reset only):**
```
Send: 60 53 41 00 XX XX XX XX 47 43 00 01 YY 0A
```
- NO calibration process started!
- Only clears `byte_20003794` flag
- Use case: Quick "fake" clear if you don't care about actual calibration
- **Warning:** Gyro accuracy may be degraded!

**Mode 2 Behavior (RECOMMENDED for SENSOR_ERROR fix):**
```
Send: 60 53 41 00 XX XX XX XX 47 43 00 02 YY 0A
```
- Full calibration runs (300 samples)
- Bias values calculated and saved to flash
- SENSOR_ERROR permanently cleared (survives reboot)
- The only mode that fully resolves SENSOR_ERROR

**Python Implementation:**
```python
def send_gyro_calibration(conn, mode=2):
    """Trigger gyro calibration.

    Args:
        conn: SAConnection instance
        mode: Calibration mode:
              0 = Calibrate (RAM only, leaves SENSOR_ERROR set)
              1 = Flag reset only (no calibration, quick "fake" clear)
              2 = Calibrate + save to flash (RECOMMENDED for SENSOR_ERROR fix)
    """
    payload = bytes([0x00, mode])
    conn.send_message('GC', payload)
    mode_names = {0: "RAM only", 1: "flag reset", 2: "flash save"}
    print(f"Gyro calibration triggered (mode={mode}: {mode_names.get(mode, 'unknown')})")

# For SENSOR_ERROR fix - use mode=2:
send_gyro_calibration(conn, mode=2)
```

**C++ Implementation:**
```cpp
enum class GyroCalibrationMode : uint8_t {
    CALIBRATE_RAM_ONLY = 0,    // Calibrate without saving (SENSOR_ERROR stays set)
    FLAG_RESET_ONLY = 1,       // Just clear flag, no calibration ("dirty hack")
    CALIBRATE_AND_SAVE = 2     // Full calibration + flash save (RECOMMENDED)
};

std::vector<uint8_t> CommandBuilder::gyro_calibration(GyroCalibrationMode mode) {
    return {0x00, static_cast<uint8_t>(mode)};
}

// For SENSOR_ERROR fix - use mode 2:
auto gc_payload = CommandBuilder::gyro_calibration(GyroCalibrationMode::CALIBRATE_AND_SAVE);
```

**When to Use Each Mode:**
| Situation                                                 | Recommended Mode                   |
|-----------------------------------------------------------|------------------------------------|
| Boot sequence                                             | **Mode 0** (see the warning below) |
| Suppress SENSOR_ERROR at runtime                          | Mode 1                             |
| Recalibrate gyro (session only)                           | Mode 0                             |
| Fix SENSOR_ERROR permanently, robot known level and still | Mode 2                             |

**Do not send mode 2 during the boot sequence.** The second gyro is not
guaranteed to have finished its own initialization at that point, and mode 2
writes whatever bias it computes to flash. A bad bias then survives every
reboot. The OEM sends mode 0 at boot for this reason.

The ESP32 hub follows the OEM: mode 0 inside the boot sequence, then mode 1
about 2 s later to clear the SENSOR_ERROR flag. Mode 2 stays a manual,
deliberate action on a robot that is level and standing still.

**Verification:**
After sending GC with mode=2, the next BC message should show:
- Type 10 (sensor error) with value != 0xFF, OR
- Type 10 completely absent from BC payload

| Offset | Size | Type  | Description                            |
|--------|------|-------|----------------------------------------|

**OnOffSensorType Values:**
| Type   | Name           | Description                           |
|--------|----------------|---------------------------------------|
| 0      | TYPE_BUMP      | Collision/bump sensors                |
| 1      | TYPE_DOWNIN    | Tilt/lift sensors                     |
| 2      | TYPE_FALL      | Wheel drop sensors                    |
| 3      | TYPE_DIRTBOX   | Dirt box presence                     |
| 4      | TYPE_CARPET    | Carpet detection                      |
| 5      | TYPE_MOP       | Mop attachment                        |
| **14** | **EStopState** | Emergency stop (published separately) |

**BYTE ORDER: resolved.** The payload is `(type, value)` byte pairs, 2 bytes per
entry. Field-verified on the GOAT G1-800: bumper and wheel-drop events decode
correctly in this order and in no other. The earlier `(value, type)` alternative
and the "verify byte order" TODO in the C++ hosts are both retired.

**Value semantics:** `value == 0` means every sensor of that type is clear.
A non-zero value is the 1-based sub-sensor index, so `value - 1` gives the
sub-type constant (BUMP_LEFT = 0, BUMP_RIGHT = 1, ...). Type 10 is the
exception: only `0xFF` is an error there, any other value is normal.

**Special Index Handling:**
- **Index 14 (0x0E):** EStopState - Published separately to `onOffInfo/EStopState` (0=normal, >0=emergency)
- **Index 10 (0x0A) with value 0xFF:** Sensor malfunction detected!

### Power Module (common::Power)

#### CC - Charge Controller (RX: 7 bytes)

| Offset | Size | Type      | Description                                 |
|--------|------|-----------|---------------------------------------------|
| 0      | 1    | uint8     | Battery percentage (0-100)                  |
| 1      | 1    | uint8     | Charge state (see below)                    |
| 2      | 2    | uint16_le | Battery pack voltage in **10 mV units**     |
| 4      | 2    | int16_le  | Charge current (mA, negative = discharging) |
| 6      | 1    | int8      | Battery temperature (deg C)                 |

**Voltage scale:** the raw uint16 is in 10 mV steps, verified against a
multimeter (raw 1890 = 18.9 V). Multiply by 10 to get mV. The value tracks the
battery pack, not the dock contact; the charge contact voltage is CO byte[0-1].

**Charge States:**
| Value | Description               |
|-------|---------------------------|
| 0     | Not charging              |
| 1     | Charging                  |
| 2     | Fully charged             |
| 3     | Charge error              |
| 4     | Charge error - switch off |

**Example:** `4b 00 6507 1fff 14`
- Battery: 75%
- Not charging
- Voltage: raw 1893 = 18930 mV = 18.93 V
- Current: -225mA (discharging)
- Temperature: 20 deg C

**MCU-Side Sender (from mcu_gkr.bin disassembly):**
- Builder: `sub_800BE84` -- sa_message_create(67, 67, 2, payload, 7)
- Prep: `sub_800BEF2` -- reads ADC, determines chargeState enum, fills payload
- Trigger: `sub_800B48C` (20ms timer task) via edge detection on `byte_2000081C`

**CC Trigger Conditions:**
- Charger connected (byte_2000081C: 0 -> 1): CC sent **2x** (countdown byte_2000065E = 2)
- Charger disconnected (byte_2000081C: 1 -> 0): CC sent **1x** (countdown byte_2000065E = 1)
- Also sent periodically during charging via `sub_8015D76` (1000ms timer task)

**Docking Detection Latency:**
CC is not polled; it fires on a charger state change with ~50-80 ms latency:
1. sub_800CF50 detects voltage threshold crossing via ADC
2. sub_800D060 (charger state machine, called every 10 IRQ_54 ticks) debounces
   with 20 consecutive readings (~30-60ms)
3. byte_2000081C flips, sub_800B48C (20ms task) detects the edge
4. CC sent on next 20ms cycle

CC byte[1] (chargeState) is the most reliable docking indicator:
0 = undocked, 1 = charging (docked), 2 = full (docked), 3/4 = error

#### CA - Charge Analog (RX: 5 bytes) -- DOCKING DETECTION

| Offset | Size | Type     | Description                                            |
|--------|------|----------|--------------------------------------------------------|
| 0      | 1    | uint8    | Flags (bit 7: 3D charger type, bit 6: charger contact) |
| 1-4    | 4    | uint8[4] | Pin signals (bits 0-2: level, bits 3-5: raw value)     |

**Docking Detection Logic (`common::Power::onSaMsgReceved` @ 0x1179f0):**

byte[0] bit 6 and bit 7 determine the `isOnCharger` field published to `power/ChargeState`:

| bit 6 | bit 7 | isOnCharger | Meaning         |
|-------|-------|-------------|-----------------|
| 0     | x     | 0           | Not on charger  |
| 1     | 0     | 1           | On charger (2D) |
| 1     | 1     | 3           | On 3D charger   |

Code: `isOnCharger = (bit6 == 0) ? 0 : (2 * bit7) | 1`

bit 7 alone is published separately to `power/ChargerType` as `std_msgs/UInt8`.

The 5 pin signal bytes are decomposed into (level, raw) pairs per pin and published
as `power/ChargeSignals` (array of `ChargeSignal` with direction/dockSignal/virtualwall).

**ROS Topics Published (from CA handler):**
- `power/ChargerType` -- uint8 (0 = 2D, 1 = 3D), only on change
- `power/ChargeState` -- {isOnCharger, chargeState}, only on change
- `power/ChargeSignals` -- pin signal array, always

**The GOAT G1-800 Main MCU (mcu_gkr.bin) never sends CA.**
No function in that firmware builds a message with ID 'C','A'. The host keeps a CA
handler, but it stays idle. Use CC (chargeState) and CO (chargeAlarm) for charger
detection. Other Ecovacs models with different MCU firmware may still send CA.

#### CO - Charge Overview / BatteryInfo (RX: 9 bytes)

Detailed battery and charging information. Published as `power/BatteryInfo` ROS topic.

**Disassembly references:**
- Handler: `common::Power::onSaMsgReceved` @ 0x1179f0, case 'O' (0x118938)
- Publisher: `a1 + 112` (offset 14)
- ROS msg type: `power::BatteryInfo_`

| Offset | Size | Type      | OEM Field Name     | Description                                              |
|--------|------|-----------|--------------------|----------------------------------------------------------|
| 0      | 2    | uint16_le | chargeVoltage      | Charge contact voltage (mV)                              |
| 2      | 2    | int16_le  | batteryCurrent     | Battery current (mA, negative = discharging)             |
| 4      | 2    | uint16_le | batteryVoltage     | Battery voltage (mV)                                     |
| 6      | 1    | uint8     | chargeStatus       | Charge state machine phase (not the CC chargeState enum) |
| 7      | 1    | int8      | batteryTemperature | Battery temperature (deg C)                              |
| 8      | 1    | uint8     | chargeAlarm        | Charge alarm/error code (0 = no alarm)                   |

**CO chargeStatus is not CC chargeState.**
These are different variables on the MCU (byte_2000064C vs byte_20003AC1).
CC chargeState is the simple 0-4 enum. CO chargeStatus is the internal charge
state machine phase (0-5), representing the multi-stage battery charging process.

**CO chargeStatus values (byte_2000064C, charge state machine):**

| Value | Phase       | MCU Handler | Description                                |
|-------|-------------|-------------|--------------------------------------------|
| 0     | Pre-charge  | sub_800AE08 | Idle / voltage check / error reset state   |
| 1     | Soft-start  | sub_800AE62 | Low-current initialization, PWM = 120      |
| 2     | CC          | sub_800AEFA | Constant Current charging, PWM 120-270     |
| 3     | CV          | sub_800AFD0 | Constant Voltage charging                  |
| 4     | Trickle     | sub_800B14A | Top-off / trickle charge, PWM = 450        |
| 5     | Maintenance | sub_800B2DC | Monitoring, can transition back to state 4 |

State machine transitions (normal charge cycle):
0 (pre-charge) -> 1 (soft-start) -> 2 (CC) -> 3 (CV) -> 5 (maintenance) -> 4 (trickle)
On error at any stage: reset to 0 with chargeAlarm set.

**ROS Message Definition (from binary @ 0x1c4398):**
```

int16  batteryCurrent
uint16 batteryVoltage
uint8  chargeStatus
int8   batteryTemperature
uint8  chargeAlarm
```

**Log format:** `battery info:%d %d %d %d %d %d`
(chargeVoltage, batteryCurrent, batteryVoltage, chargeStatus, batteryTemperature, chargeAlarm)

**Note:** CO provides more granular charge data than CC. CC gives battery percentage
(0-100) and a simple charge state enum (0-4). CO gives raw voltages, current, the
internal charge phase (0-5), and an alarm code. The chargeStatus fields use DIFFERENT

#### Charger Detection Pipeline (MCU-side, from mcu_gkr.bin)

Complete call chain from physical charger contact to SA message on UART:

```
IRQ_54 (timer interrupt, ~3.5kHz)
  |
  +-- every 10 ticks: sub_800D060 (charger state machine)
  |     |
  |     +-- sub_800CF50: ADC read charge contact voltage
  |     |     |
  |     |     +-- voltage > threshold: byte_20000652 = 1 (triggers CO)
  |     |     +-- voltage < threshold: byte_20000652 = 1 (triggers CO)
  |     |
  |     +-- debounce counter byte_200007CA (needs 20 consecutive readings)
  |     +-- when counter reaches +/-20: byte_2000081C flips (charger state)
  |
  +-- every 35 ticks: motor PID + encoder read

20ms Timer Task: sub_800B48C (charge report dispatcher)
  |
  +-- edge detect on byte_2000081C (charger contact flag)
  |     |
  |     +-- rising edge (0->1, docked):  byte_2000065E = 2 (send CC 2x)
  |     +-- falling edge (1->0, undocked): byte_2000065E = 1 (send CC 1x)
  |
  +-- if byte_2000065E > 0: call sub_800BEF2 (CC sender), decrement
  +-- if byte_20000652 == 1: call sub_800C18E (CO sender), clear flag
```

**Dock Event Timeline (physical contact to message on UART):**

| Time      | Event                                                                    |
|-----------|--------------------------------------------------------------------------|
| 0ms       | Charger pins make physical contact                                       |
| ~3ms      | sub_800CF50 detects voltage crossing, sets CO trigger flag               |
| ~20ms     | CO sent (next 20ms task cycle): chargeVoltage/batteryCurrent/chargeAlarm |
| ~30-60ms  | Debounce completes (20x sub_800D060 readings), byte_2000081C = 1         |
| ~50-80ms  | CC sent (next 20ms task cycle): chargeState = 1 (CHARGING)               |
| ~70-100ms | CC sent again (2nd of 2x on connect)                                     |

**Undock Event Timeline:**

| Time     | Event                                                      |
|----------|------------------------------------------------------------|
| 0ms      | Charger pins lose contact                                  |
| ~3ms     | sub_800CF50 detects voltage drop, sets CO trigger flag     |
| ~20ms    | CO sent: chargeVoltage drops to 0                          |
| ~30-60ms | Debounce completes, byte_2000081C = 0                      |
| ~50-80ms | CC sent (1x on disconnect): chargeState = 0 (NOT_CHARGING) |

**For ROS2 implementation:** Use CC chargeState (byte[1]) as the primary docking
indicator. CO arrives earlier but only carries voltage/alarm data without a clean
state enum. CA is not sent by this MCU firmware version.

**SA Protocol Frame Format (via `sa_tx_frame_send` @ 0x80086AE):**
```
0x60 + 'S' + 'A' + [header1] + [header2] + [payload...] + 0x0A
  |     |     |       |           |           |            +- Newline (frame end)
  |     |     |       |           |           +- PIN code (2 bytes, uint16_le)
  |     |     |       |           +- 'C' (0x43) - from text_obj offset 14
  |     |     |       +- 'Z' (0x5A) - from text_obj offset 13
  |     |     +- 'A' (0x41) - SA wrapper
  |     +- 'S' (0x53) - SA wrapper
  +- Backtick (frame start)
```

**Escape Handling:** The `sa_tx_frame_send` function applies escape sequences:
- `0x5C` -> `0x5C 0x01`
- `0x60` -> `0x5C 0x02`
- `0x0A` -> `0x5C 0x03`

**Also triggered from:**
- `ui_page_alarm_enter` @ 0x800DC1C, 0x800DC6A (Alarm PIN entry)

## Host Implementation Notes

Collected from the ESP32 hub, which drives the Main MCU over SA protocol in
place of the OEM Linux board. Every value here is measured on a GOAT G1-800.

### TX cadence

| Message           | Interval                          |
|-------------------|-----------------------------------|
| HA                | 150 ms idle, 500 ms while driving |
| WA                | 20 ms floor while driving         |
| MA (cut motor)    | 500 ms while the blade should run |
| DO (e-stop clear) | 500 ms x 20 tries, then 5 s       |

The 300-400 ms HA figure from the OEM captures also works. A shorter idle
interval keeps the motor watchdog clear of its limit at no real cost.

WA is a repeated command, not a setpoint: a gap longer than the wheel watchdog
stops the wheels. 20 ms is a floor, so the WA rate never exceeds 50 Hz.

The DO retry is keyed on the e-stop state reported in BC, never on the DO echo.
A host-side command timeout of 200 ms on the incoming velocity stream keeps a
dead controller from leaving the last WA in force.

### Heartbeat timeout value

`HA` payload 50 gives a 20 s watchdog (50 x 400 ms) and is what the hub uses.
The OEM sends 2 (~0.8 s). Both are accepted. A short timeout turns any host
stall into an immediate motor cut-off, so pick it to match the host's own
watchdog rather than copying the OEM value.

### Wheel speed units

WA speed values are encoder ticks per second. For this chassis:

| Quantity                            | Value    |
|-------------------------------------|----------|
| Ticks per wheel revolution          | 2492     |
| Wheel radius                        | 0.1105 m |
| Ticks per metre                     | 3589     |
| Observed OEM maximum (1074 ticks/s) | 0.30 m/s |

### Dock contact from CO

CO byte[0-1] (charge contact voltage) is the earliest dock signal, roughly
20 ms after physical contact and before the CC debounce completes. A latch with
hysteresis on that voltage is stable in the field:

| Threshold | Value         | Effect                         |
|-----------|---------------|--------------------------------|
| Set       | >= 12000 mV   | Dock contact established       |
| Clear     | < 9000 mV     | Dock contact released          |
| Between   | 9000-12000 mV | Latch holds its previous state |

The set level sits below the MCU assert level so a sagging dock supply still
registers. CO also fires on every 1 % battery SOC step and on charge alarms, so
a CO arrival by itself is not a dock event; compare the voltage against the
latch.

### Top MCU scope

The Top MCU sections of this document describe the OEM GD32 firmware. Robots
running replacement top-board firmware do not produce ZR rain messages, KA key
events, or the `@`-prefixed ASCII commands. Their rain and button data arrive
over whatever protocol that firmware defines.

## Safety Notes

1. **Always send heartbeats** - without HA messages every ~400 ms the MCU disables the motors
2. **Stop on exit** - Always call `stop_wheels()` and `stop_all_motors()` before closing
3. **Exclusive port access** - Use exclusive mode to prevent conflicts
4. **Handle serial errors** - Hardware UARTs can report readiness but return no data
5. **Use WA for driving** - MA addresses auxiliary motors only

## Top MCU Firmware Details (GD32F103C8T6)

The Top/Screen MCU (`/dev/ttyS3`) uses an **ASCII wrapper** around SA Protocol messages.
Full reverse engineering details are in `../Docs_Top_MCU/Pin_Definitions.md`.

### ASCII Frame Format (Top MCU Internal)

```
@<CMD><PAYLOAD>*
|  |      |     +- Frame End (0x2A = '*')
|  |      +- Hex-encoded payload bytes
|  +- 2-char command ID
+- Frame Start (0x40 = '@')
```

### Top MCU Commands (ASCII Wrapper)

| Cmd | SA Equivalent | Direction | Description                           |
|-----|---------------|-----------|---------------------------------------|
| Bc  | -             | RX        | FCT Mode ON/OFF (`@Bc01*` enters FCT) |
| Da  | -             | RX        | Display Mode control                  |
| Ea  | ZG            | RX        | Display Power ON/OFF                  |
| Fa  | ZG            | RX        | All Points ON/OFF                     |
| Ga  | ZG            | RX        | Inverse Display ON/OFF                |
| Ha  | ZG            | RX        | Backlight ON/OFF                      |
| Ka  | KA            | TX/RX     | Key Event (TX: `@KaA0*` = key 0xA0)   |
| Ra  | -             | TX/RX     | Relay Mode (see below)                |
| Sa  | -             | RX        | Screen Mode control                   |
| Va  | VB            | TX        | Version response                      |
| Pa  | -             | TX        | Protocol info response                |

Notes:
- RX commands (Da/Ea/Fa/Ga/Ha/Ka/Ra/Sa/Va/Pa) are accepted only when FCT is active (`g_display_mode == 1`).
- `@Bc01*` enters FCT; `@Bc00*` exits and clears mode flags.
- `@Da01*` sets `g_mode_display = 1` and disables keyevent/relay/screen modes; `@Da00*` clears only `g_mode_display`.
- Display control mapping: `Ea` -> 0xAF/0xAE, `Fa` -> 0xA5/0xA4, `Ga` -> 0xA7/0xA6, `Ha` toggles PA0 via GPIOA BSRR/BRR (backlight).

### Relay Mode (`@Ra`) - Rain Sensor Passthrough

Relay Mode allows the Linux SBC to monitor the Rain Sensor (PA1) state directly.

**Enable/Disable:**
```
@Ra01* -> Enable Relay Mode (disables display, keyevent, screen modes)
@Ra00* -> Disable Relay Mode
```

**Response (MCU -> SBC, periodic when enabled):**
```
@Ra00* -> Rain not detected (PA1 mostly HIGH)
@Ra01* -> Rain DETECTED (PA1 >30% LOW in 10 sec window)
```

**Detection Logic** (`rain_sensor_detect_pa1` @ `0x8008EEA`):
- Reads PA1 every 5ms (rain sensor input, active-low = water detected)
- Counts samples with PA1 LOW over 2000 samples (10 sec window)
- Sets `g_rain_sensor_state = 1` if >600 samples were LOW (~30% threshold)

| **Spot turn CW**    | 0x00 (FWD) | 0x01 (REV) | Same speed, opposite directions                    |
| **Spot turn CCW**   | 0x01 (REV) | 0x00 (FWD) | Same speed, opposite directions                    |
| **Stop**            | 0x02       | 0x02       | Both speed = 0                                     |

**Speed Ranges Observed:**
- Maximum forward speed: 1074
- Typical reverse speed: 358-945
- Spot turn speed: 232-419

**Turning Logic:**
- Forward: Slower wheel determines turn direction (L slower = turn left)
- Reverse: Faster wheel determines turn direction (R faster = turn right while reversing)
- Spot turn: Wheels rotate in opposite directions for zero-radius rotation

## WA Payload Structure (from Main MCU firmware analysis)

Confirmed from `sa_handle_wheel_action_WA` @ 0x80141FA in mcu_gkr.bin.

Total payload: 19 bytes.

| Offset | Size | Type    | Description                                            |
|--------|------|---------|--------------------------------------------------------|
| 0      | 1    | uint8   | Sub-command (always 0x00)                              |
| 1      | 1    | uint8   | Left direction: 0x00=forward, 0x01=reverse, 0x02=stop  |
| 2      | 4    | float32 | Left wheel speed (cm/s, endianness TBD)                |
| 6      | 4    | float32 | Right wheel speed (cm/s, endianness TBD)               |
| 10     | 1    | uint8   | Right direction: 0x00=forward, 0x01=reverse, 0x02=stop |
| 11     | 4    | float32 | Left angular speed (unused in captures, set to 0.0)    |
| 15     | 4    | float32 | Right angular speed (unused in captures, set to 0.0)   |

Firmware conversion: `internal_pwm = speed_cm_s * 29.1` (float constant 0x41E8CCCC).
PWM output is clamped to +/-1400 by the PID controller (motor_pid_controller @ 0x8009EC0).
Max useful speed: ~48 cm/s (48 * 29.1 = 1396.8, just under 1400 clamp).

Note: The 4-byte speed values are read via memcpy (sub_8006AB4), then converted
through sub_8007AB4 and multiplied by 29.1.

**Conflict with field practice -- use the uint16 encoding.**
The float32 reading above and the uint16_le encoding in the WA TX section
disagree, and only the uint16 encoding is proven on hardware:

- The ESP32 hub sends `uint16_le` at offsets 2-3 and 11-12 with the remaining
  bytes zero, and the robot drives at the commanded speed. Read as float32,
  those same bytes are a denormal (0x00000432 = 1.5e-42), which would command
  a standstill.
- The speed unit is **encoder ticks per second**, not cm/s. With 2492 ticks per
  revolution and a 0.1105 m wheel radius, 1074 ticks/s = 0.30 m/s, which matches
  the OEM top mowing speed. Read as cm/s, 1074 would be 10.7 m/s.

Treat the float32 decompilation as an unresolved reading of the handler, not as
the wire format. The 29.1 factor and the +/-1400 PWM clamp still describe the
internal PID scaling.

## DO - EStop Control (TX: 2 bytes)

Confirmed from `sa_handle_DO_estop_control` @ 0x801430E.

The DO message uses the second character of the message ID as sub-type.
The handler at 0x801430E dispatches all messages starting with 'D':

| Message ID | Sub-Type | Payload | Description                   |
|------------|----------|---------|-------------------------------|
| DD         | 'D'      | 2 bytes | Basic relay (forwarded as-is) |
| DE         | 'E'      | 3 bytes | Extended relay                |
| DO         | 'O'      | 2 bytes | E-Stop control                |

The sub-type byte is read from offset 14 of the parsed message struct,
which corresponds to the second character of the message ID (not a
payload byte). The payload itself contains only the command data.

E-Stop Clear (message ID "DO"):
- Payload: `[0x00, 0x01]` (2 bytes, no sub-type prefix)
- Firmware checks: `payload[0] == 0 AND payload[1] == 1` -> calls `estop_clear()`
- Effect: sets `g_estop_sensor_status = 0`, clears bit 0x0020 in `g_emergency_flags`
- MCU echoes a DO message containing [payload[0], payload[1]] for **every** DO it
  receives, whether or not a bit was actually cleared. The echo is a receipt, not
  a success confirmation -- do not end a retry loop on it. Key the retry on the
  e-stop state reported in BC type 14 instead.
- DO clears bit 0x0020 only. A bumper never raises that bit, so DO cannot free a
  latched bumper (see the Emergency System section).
- After clearing, motors must be re-armed with WA stop (speed=0) + HA heartbeat

Leave sub-type 0x4F out of the payload. The sub-type is already encoded in
the message ID "DO". Including it makes payload[0] read 0x4F instead of 0x00,
and the clear condition then fails without any error report.

## BC - OnOff Sensor Array (RX: variable)

Sensor type IDs confirmed from `bc_sensor_table_init` @ 0x8015886.

Payload consists of `[sensor_type (uint8), sensor_value (uint8)]` entries,
2 bytes each -- the same encoding as the OnOffInfo section above. The internal
MCU table holds the type as uint16, but only the low byte reaches the wire.

| Type ID | Name         | Values                                                  |
|---------|--------------|---------------------------------------------------------|
| 0       | Bump sensor  | 0=clear, non-zero=1-based sub-sensor index              |
| 2       | Fall sensor  | 0=clear, 3=both wheel-drop sensors triggered            |
| 10      | Sensor error | 0xFF=error (missing gyro calibration), anything else ok |
| 14      | E-Stop       | 0=released, 1=pressed                                   |

Note: The sensor table is initialized with up to 9 entries. Additional sensor
types beyond these four may exist on different board variants.

**Fall sensor practice:** a single-sided fall bit is an unreliable cliff signal.
Field logging on the GOAT G1-800 counted 151 right-side-only assertions against 0
left-side-only ones over one session with no real cliff present; direct sunlight
into the IR receiver reproduces it. Treat only "both sides triggered" as a
cliff.

## Emergency System (Main MCU internal)

Confirmed from `emergency_check_and_handle` @ 0x800D818.

The MCU maintains a 16-bit emergency flags register (`g_emergency_flags` @ 0x20000788).
When ANY bit is non-zero, `motor_emergency_stop()` is called every cycle.

| Bit | Mask   | Source                                     | Auto-Clear                   |
|-----|--------|--------------------------------------------|------------------------------|
| 0   | 0x0001 | Gyro tilt (abs > 35, 10 cycles)            | Yes, with counter            |
| 1   | 0x0002 | Fall sensor persistent (350 cycles)        | Yes, when sensor clears      |
| 2   | 0x0004 | Gyro severe (abs > 100, 25 cycles)         | Yes, with counter            |
| 3   | 0x0008 | Held bumper (sub_800D77C, ~9 s of contact) | No, physical release only    |
| 5   | 0x0020 | E-Stop sensor                              | No, requires DO [0x00, 0x01] |
| 7   | 0x0080 | External sensor check                      | Yes                          |
| 8   | 0x0100 | Activity timeout                           | Yes, with countdown          |
| 9   | 0x0200 | Sensor error counter                       | Yes                          |
| 10  | 0x0400 | Delayed error                              | Yes, after 250 cycles        |
| 11  | 0x0800 | No heartbeat / motor activity              | Yes, with HA/WA messages     |
| 15  | 0x8000 | Persistent error                           | No                           |

The E-Stop bit (0x0020) is the only bit an SA message can clear. Bit 0x0008 has
no clear command at all, and the remaining bits auto-clear when their trigger
condition resolves.

### Held-bumper escalation (mcu_gkr 1.5.6)

A bumper that stays pressed escalates in two steps inside the LL MCU:

| Time in contact | Effect                                                                | Recovery                            |
|-----------------|-----------------------------------------------------------------------|-------------------------------------|
| ~0.7 s          | sub_800D77C blocks forward motion; reverse and rotation still execute | Release, or drive out backwards     |
| ~9 s            | emergency bit 0x0008 set; every direction is blocked                  | Physical release of the bumper only |

DO [0x00, 0x01] does not help here: a bumper raises bit 0x0008, and
`estop_clear()` masks bit 0x0020.

**WA gate (sub_800DA50).** While forward motion is blocked, the MCU still accepts
a WA command whose two wheel speeds satisfy `left + right <= 0`. Rotation in
place (equal and opposite speeds, sum zero) passes. A host that mutes WA entirely
on a bumper contact removes its own escape route and lets the ~9 s timer run out.
The working retreat is an arc: the pressed side sets the yaw sign so the nose
swings away from the obstacle, because a straight reverse keeps a side bumper
pressed.
